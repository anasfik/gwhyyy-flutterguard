Flutter APK inspection: reading a release on Android

A Flutter package can be read on the phone that runs it. No root, no workstation, no upload. The useful checks fit in one careful pass over the manifest, the compiled library and the assets.

By Anas Fikhi · 2 November 2026 · 7 minute read

In short. Read the manifest first for policy, then lib/<abi>/libapp.so for strings and symbols, then flutter_assets/, the dependency notices and the signing certificate. Nothing has to run, and nothing has to leave the device.

Before you start

Inspect only an app you own or have written permission to test. The techniques below are read-only, but authorisation is still the boundary between an audit and an intrusion. Keep findings local while you triage, and mask any value that looks like a credential.

You need the APK, an Android device or emulator, and a tool that can open a package. On the phone, FlutterGuard does the reading in place. On a workstation, apktool, jadx, unzip and strings cover the same ground with more setup.

Get the APK

There are three honest sources:

  • Your own build. Run flutter build apk --release and inspect the artifact you are about to publish. This is the cleanest baseline because you know the commit and the build flags.
  • A downloaded artifact. Use the publisher's official release channel. Do not treat a mirror as authoritative; verify the signature and the version.
  • An installed app on a device you control. Tools that read installed packages can list the APK path the package manager exposes. On many Android versions, pulling another app's base APK over adb fails without root, so a package reader on the device is the practical route.

An AAB is a publishing format, not an installable package. Convert it with bundletool before inspection, or audit the APK that was generated from it.

Read it in five passes

1. Manifest and policy

Start with package identity, permissions and exported components. Then check intent filters, backup settings, debuggable flags, cleartext traffic and any network security configuration. These are policy decisions, so they are easier to judge than a random string.

2. Compiled Dart

lib/<abi>/libapp.so holds the AOT snapshot. It is machine code, not recoverable Dart source, but it keeps string literals and symbol metadata. Look for URLs, hostnames, header names, key-like values and package: references. Symbol readability also tells you whether the build used --obfuscate.

3. Assets

flutter_assets/ is a file tree. Read the asset manifest, fonts, JSON, images and NOTICES.Z. Bundled configuration is public configuration. If a file would be embarrassing in a zip, it should not be in the APK.

4. Dependencies

License notices, package: URIs and readable symbols identify Dart packages and native SDKs. Version evidence is often incomplete, so record confidence with each entry. Prioritise components that touch authentication, payments, analytics, WebView bridges and AI providers.

5. Signing

Read the certificate and the signature schemes. A debug certificate on a distributed release is a process failure. A changed certificate between versions can also explain why an update was rejected.

Doing it with FlutterGuard

  1. Install the APK from the GitHub release (opens in a new tab) on the device.
  2. Choose an installed Flutter app or open a single APK.
  3. Run the scan and review the sections in the order above: policy, strings, assets, structure, signing.
  4. Reveal a masked value only when you need to judge it, and never paste it into a public issue.
  5. Save the report as JSON or Markdown if you need a record. Reports stay in the app's private storage; uninstalling removes them.

The app has no INTERNET permission, so nothing leaves the device. That also means no cloud lookups, no reputation service and no automatic CVE matching. The report is evidence for your own review.

Doing it on a desktop

When you need a workstation, these commands cover the first pass. Run them in a directory that contains only the APK you are authorised to inspect.

unzip -l app-release.apk

apktool d app-release.apk -o decoded

strings lib/arm64-v8a/libapp.so \
  | grep -Ei 'https?://|api[_-]?key|token|secret' | head -50

The manifest is binary XML. apktool, aapt2 dump or apkanalyzer will decode it; plain cat will not. A desktop scanner like MobSF wraps these steps and adds scoring, but its generic rules produce false positives on Flutter apps because it cannot see Dart source. Use scores as a queue, not a conclusion.

Triage without false alarms

  • Public client keys. Firebase and Supabase anon keys are designed to ship. Check the server rules that constrain them instead of reporting the key alone.
  • Placeholders and test values. A string like YOUR_API_KEY or pk_test_ is not a live secret. Read the context before escalating.
  • Version guesses. A package name in a notice file does not prove a vulnerable version. Confirm the version from a reliable artifact before citing a CVE.
  • Endpoints. A production API host is expected. A staging host, an admin path or a public bucket is worth verifying against your own systems.
  • Reachability. An exported component is a surface, not an exploit. Confirm the path and the impact with a dynamic test you are authorised to run.

Static evidence has a ceiling. It cannot prove authentication is missing, observe runtime behaviour or confirm exploitability. Report what you saw, where it lives, and what would verify it. See the full checklist for Flutter app security.

Questions people ask

Can I inspect a Flutter APK without a computer?

Yes, on Android. A package reader that can open a file you pick, or list the APKs the package manager exposes, is enough. FlutterGuard does the reading in place and keeps the report on the phone.

Where is the Dart code inside a Flutter APK?

In lib/<abi>/libapp.so, as ahead-of-time machine code with string literals and symbol metadata. It is not recoverable Dart source, and it is not in classes.dex, which holds the Android shell and plugin code.

Do I need root to inspect an installed app?

No. Opening an APK file you selected works on any device. Pulling another app's base APK over adb usually needs root, which is why an on-device reader is the practical route.

What should I check first in a Flutter APK?

Manifest policy: exported components, backup, debuggable and cleartext settings. Then hostnames and key-like strings in the compiled library, then assets, dependencies and the signing certificate.
