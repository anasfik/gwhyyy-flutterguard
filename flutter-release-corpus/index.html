What 26 released Flutter apps expose

Public release APKs, read twice: once on a workstation and once on a phone. These are the counts, the method and the limits of what static inspection can say.

By Anas Fikhi · 18 November 2026 · 10 minute read

Most Flutter security advice is written about source code. This corpus is about what ships. Every figure below comes from a public release artifact, inspected without executing it. The numbers describe a sample, not the Flutter ecosystem: 26 APKs collected from projects' own release pages, plus a device pass on one app to test what a host-only scan misses.

What a match means. A provider host or SDK marker in an APK proves the string is present in the artifact. It does not prove the code path runs, that a key is valid, or that the app is insecure. No live secrets, app rankings or accusations are published here.

How the corpus was built

  • Two collections. An initial set of 11 Flutter apps plus one non-Flutter control, each audited with host tools and with the FlutterGuard app on a device. A second set of 22 production APKs downloaded from the projects' own GitHub release pages.
  • One gap study of 26 release APKs combines both collections where the questions overlap.
  • Classification check. 33 Flutter apps of 306 installed apps were identified from package contents, with no misses recorded in that pass.
  • Host tooling. aapt2 for the manifest, unzip for assets, strings for the compiled Dart library, plus the app's own parsers for the same artifact.
  • Measured 2026-10-30. Detector rules changed after these counts; re-running the corpus produces different totals.

AI provider endpoints

FlutterGuard carries 109 literal provider hosts, covering the common inference APIs and local runtimes. 9 of 26 apps matched at least one host.

The AppFlowy result is the useful kind of surprise: both hosts are local model runtimes, which a generic scanner has no reason to flag. The other matches show that a Flutter app can carry a broad provider surface without any of it being visible in the Dart source structure a reviewer would search.

An early version of the host detector only collected strings containing ://. That missed hostnames stored without a scheme and produced a partial result on the same app. Fixing it changed one device result from 4 provider hosts to 23.

Native SDK markers in the DEX

Flutter moves application logic into libapp.so, but plugins and the Android embedding still land in classes.dex. A sweep of 82 known prefixes matched 22 of 26 apps.

WebView bridges and billing code are the entries worth attention in a review: one crosses a JavaScript boundary, the other touches money. Presence is not proof of a vulnerable version. It is a queue for the next question.

What is usually absent

A bundled assets/flutter_assets/pubspec.yaml appeared in 1 of 26 apps: Anx Reader 1.14.0+6321, with 92 declared dependencies. Root .properties files with Flutter and SDK markers were more common and are enough to identify a release build. The practical lesson is that dependency inventory usually has to be reconstructed from notices, package: strings and readable symbols rather than read from a manifest.

Workstation pass versus device pass

One app, Conduit, was scanned on a Redmi Note 9 Pro running API 35. The device pass reads the installed package the same way the host pass reads a downloaded APK, and the two results differed because of what each file set contains.

SignalHost scanDevice scan
Third-party services1528

Provider hosts423

The 17 providers on the device were OpenAI, Anthropic, Gemini, OpenRouter, DeepSeek, Groq, Mistral, Cohere, Together, Fireworks, Perplexity, xAI, HuggingFace, Alibaba Qwen/DashScope, Moonshot, Zhipu GLM, and the Ollama/LM Studio local runtime pair. The gap came from the scheme-dependent host detector described above, not from the device exposing a different application.

What this changes in practice

  • A DEX-only review under-reports a Flutter app. The interesting strings sit in libapp.so and in assets.
  • A source review under-reports a release. Provider hosts, bundled assets and manifest policy survive the build and are only visible in the artifact.
  • Obfuscation does not remove literals. The corpus relies on string data that survives --obfuscate.
  • Device and host passes are complementary. Run the pass on the artifact users install.

Limits

  • 26 APKs is a sample. It supports statements about these artifacts, not a prevalence rate for Flutter apps.
  • Counts depend on the detector version. Provider rules grew from 35 to roughly 135 services during this work.
  • A string match is evidence of presence. Behaviour, key validity and exploitability need a dynamic test.
  • Only public release artifacts were used. The corpus publishes counts and a few illustrative hosts, never credentials.
  • Artifacts rotate. Re-downloading a project's current release can produce a different result from the one recorded here.

The full method and per-app notes live in the app repository: CORPUS.md (opens in a new tab). If you repeat the study, start from the same public release pages and record the artifact hash. The release checklist turns these signals into a review process, and the inspection guide covers the commands.
