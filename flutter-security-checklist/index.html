Flutter app security audit checklist

A working checklist for the release you are about to hand over. It runs against the APK, not the repository, because the artifact is what users install.

By Anas Fikhi · 18 November 2026 · 9 minute read

Use this in order. Each group ends with a decision you can write down: pass, lead to verify, or accepted risk. The whole pass is read-only and needs no running backend. Run it on the signed artifact you publish, once per release, and keep the result with the version and certificate.

Scope. Only inspect apps you own or are authorised to assess. Static inspection shows what shipped; it does not prove that a string is used, that an endpoint is reachable, or that a component is exploitable.

1. Artifact and identity

  • Confirm the artifact is the release. Check the version name and code, the build type and the signing certificate. A debug certificate on a distributed build is a process failure, not a finding to triage.
  • Record the certificate digest. It is the baseline for the next release. A changed certificate explains rejected updates and breaks trust with existing installs.
  • Note the Flutter engine and ABI set. Split APKs and app bundles change which files land on a device; inspect the APK that is actually served.
  • Keep the artifact hash. One SHA-256 per release makes later comparison and reporting unambiguous.

2. Manifest and Android policy

  • List permissions and justify each one. A permission is not a vulnerability by itself, but an unexplained one is a conversation.
  • Review exported components. Activities, services, receivers and providers with android:exported="true", plus the intent filters that reach them.
  • Check backup and debugging flags. android:allowBackup, android:debuggable and any test-only attribute that survived the release build.
  • Check cleartext traffic. android:usesCleartextTraffic and the network security configuration, including per-domain exceptions.
  • Read the deep-link surface. Every scheme and host an external app can target, and whether the target validates its input.

3. Exposed data

  • Search the compiled Dart library. lib/<abi>/libapp.so keeps string literals even after --obfuscate. Look for keys, tokens, passwords and private URLs.
  • Search the assets. Bundled JSON, .env files, configuration and fixtures are extractable with the APK.
  • Treat compile-time values as public. Anything supplied through --dart-define or String.fromEnvironment is in the binary.
  • Mask before you share. Triage with values redacted; reveal a value only to judge it, and never in a ticket, chat or report attachment.
  • Verify before escalating. A client key may be designed to ship. Check the server-side rules that constrain it before calling it a secret.

4. Dependencies and native SDKs

  • Build the component list. Use NOTICES.Z, package: strings and readable symbols to identify Dart packages and native SDKs.
  • Mark confidence per entry. Version evidence from an APK is often partial. A package name is not a version, and a guessed version is not a CVE.
  • Prioritise the security-relevant set. Authentication, payments, analytics, WebView bridges, ad SDKs and AI providers matter more than a font package.
  • Check for an unexpected environment. A staging SDK key, a sandbox endpoint or an internal host points at a build-configuration problem.

5. Endpoints and network surface

  • Collect hosts and base URLs from the library, assets and manifest. Group them by owner: your domain, a provider, a CDN, an analytics service.
  • Flag what should not ship. Staging hosts, admin paths, internal hostnames and buckets with anonymous write access.
  • Check TLS posture where you can see it. Pinning configuration and cleartext exceptions are visible statically; whether pinning can be bypassed is a dynamic question.
  • Test only your own systems. A host in an APK is a lead. Probing someone else's infrastructure is not part of an audit.

6. Signing and distribution

  • Verify the signature scheme. Confirm the APK is signed and note which schemes are present.
  • Compare with the previous release. Certificate, package name and version code continuity.
  • Check the distribution channel. Play App Signing, a GitHub release or an internal track each change what the certificate means.
  • Confirm the published artifact matches the tested one. Compare the SHA-256 of the file users download with the file you inspected.

7. Report and handover

  • Write one line per item: what was checked, what was found, and where in the artifact it lives.
  • Separate evidence from impact. "Readable staging host in libapp.so" is evidence. "Backend is exposed" is a claim that needs a test.
  • List the open questions. Runtime checks, authentication tests and server configuration that static review cannot answer.
  • Keep a baseline. The next audit starts by diffing against this report, not from zero.

What the checklist cannot prove

It cannot observe runtime behaviour, intercept traffic, test authentication or confirm exploitability. Server-side authorisation, rate limits and data exposure sit outside the APK. A report is strongest when every item names its source and says what would confirm it. The Flutter security guide explains the reasoning behind each group; the APK inspection how-to covers the phone workflow and the source-built CLI.

Run it on a device or from a terminal

FlutterGuard performs groups 1 to 6 on an Android phone, without a desktop and without executing the app. It groups findings by artifact, policy, data, dependencies, endpoints and signing, then saves the report as JSON or Markdown. The app has no INTERNET permission, so the evidence stays local.

The source-built CLI performs the same static checks from a terminal and writes redacted JSON or SARIF, so the same groups can run in CI. It takes one APK per invocation and has no comparison command; use the Android app for release-to-release comparisons of the same package.

Take the checklist to the release.

Install from Google Play, or use the APK from GitHub if you need a specific build. The CLI is built from source with JDK 17 or newer.
