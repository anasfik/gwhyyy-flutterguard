Look beyond the manifest.

A Flutter release carries evidence in its compiled library and assets, too. Read those layers together before deciding what needs attention.

  • 01 / Libraries

    Know the building blocks.

    Identify SDKs, dependencies, native libraries and available version evidence.

  • 02 / Connections

    See where it points.

    Explore embedded endpoints, domains and AI-provider references. A string does not prove a live connection.

  • 03 / Exposed strings

    Find what was left in.

    Review secret-pattern matches with values masked by default. Check a lead before treating it as a credential.

  • 04 / Package policy

    Inspect the guardrails.

    Read permissions, signing metadata and network policy. Signing metadata is not cryptographic verification.

  • 05 / Flutter evidence

    Read the packaged clues.

    Inspect assets, candidate routes and recognised Dart snapshot metadata, with unsupported details left unknown.

  • 06 / Reports

    Keep a useful record.

    Save Android audits and export JSON or Markdown. Use the CLI for redacted JSON and SARIF reports.

Know what a finding proves.

Version 0.4.0 separates observed facts from things worth investigating. Severity and confidence answer different questions.

Confirmed artifact facts
Directly observed in the release. These establish what shipped, not whether it can be exploited.
Leads worth checking
Pattern matches and heuristics that need context. Unknown rules default to suspected, not confirmed.
Inventory
Useful package information to explore, without presenting every item as a security problem.

Only confirmed findings affect the grade. An A is a summary of those checks, not a security certificate.

Build from source

In your terminal or CI

Scan an APK without an Android device. Keep JSON for your tooling, or produce SARIF for a review workflow.

After building the CLI · JDK 17+

cli/build/install/flutterguard/bin/flutterguard scan app.apk \
  --json report.json \
  --sarif report.sarif \
  --fail-on confirmed

Exit 0: scan completed. 1: confirmed-finding gate hit. 2: error. A gate hit means an artifact fact, not a confirmed exploit.

Output files must be new, with an existing parent directory. Build and launcher instructions are in the guide.

Build and use the CLI ↗

Scans stay local. Uploading reports as CI artifacts is a separate choice; check your provider’s access and retention settings.

Moving between versions or install channels?

Play and GitHub use different signing channels. GitHub releases before 0.3.4 used another key: updating those installs requires an uninstall, which deletes saved reports, history and settings. Export anything you need first; exports cannot restore that history. Check the install-channel notes before switching.

One engine, reusable in your own tools.

The Android app and CLI use the same pure-JVM :engine module. Build it from source to integrate scans into JVM tooling; it is not a separately published package.

A few things worth knowing.

Clear boundaries make the report more useful. Here is what to expect before your first scan.

Is FlutterGuard free?

Yes. The Android app, CLI and engine are open source under the MIT licence. There is no account or paid tier.

Does my APK leave my machine?

Scans run locally. The Android app has no INTERNET permission, and the CLI does not upload APKs. Building the CLI can download dependencies. If you upload reports from CI, your CI provider stores those artifacts.

Which files and apps can I inspect?

Inspect Flutter apps you own or are authorised to test. Android can read accessible installed apps or a single APK; the CLI accepts a single APK. Convert AABs to APKs first. Device restrictions can prevent installed-app access.

Does a confirmed finding prove a vulnerability?

No. Confirmed means a fact observed in the packaged artifact, not a working exploit, valid credential or reachable service. Only confirmed findings affect the grade. A good grade does not certify security.

Can I compare releases from the CLI?

Release comparison is available in the Android app for scans of the same app. The CLI currently scans and exports; it does not have a compare command.

Does it recover Dart source code?

No. It reads packaged evidence, strings and recognised snapshot metadata. It does not reconstruct Dart source, trace runtime behaviour or prove whether a release is obfuscated.

How do I get the latest version?

GitHub has the 0.4.0 Android APK. Public Google Play was last verified at 0.3.2 on 20 November 2026; check the store for its current version. Build the CLI and engine from source. Installation and signing caveats are above.
