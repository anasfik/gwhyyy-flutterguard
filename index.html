Attack surface

What I inspect

Focused on what survives compilation, what crosses the Flutter/native boundary, and what becomes useful once someone has your release file.

01

APK / AAB anatomy

Package metadata, versions, SDK levels, ABIs, native libraries, assets, Flutter evidence, and release/build signals.

02

Manifest attack surface

Permissions, exported activities, services, receivers, providers, cleartext settings, debug flags, backup, and deep links.

03

Secrets & exposed configuration

Hardcoded credentials, API keys, environment remnants, URLs, Firebase, Supabase, service configuration, and staging infrastructure.

Context matters. A Firebase API key is not automatically a secret or a vulnerability.

04

Flutter artifacts / libapp.so

Readable strings, backend hosts, implementation clues, feature flags, channel names, environment indicators, and release information surviving AOT compilation.

05

Network & backend boundary

Hosts, transport configuration, network security config, certificate trust, pinning context, API assumptions, and client/server trust boundaries.

Lack of certificate pinning is not automatically a vulnerability. Architecture and threat model decide.

06

WebViews & platform bridges

WebViews, JavaScript, URL handling, native Java/Kotlin wrappers, MethodChannel, EventChannel, JavaScript bridges, and trust boundaries.

07

Signing & release posture

APK signatures, certificate identity, debug certificate indicators, release configuration, and distribution/build hygiene.

08

Third-party SDK/service surface

Firebase, Google Maps, AWS, Sentry, Stripe, RevenueCat, OneSignal, Supabase, and analytics SDKs.

Presence is not vulnerability. Human review determines exposure and impact.

Method

I review the app from the outside in.

Same starting point an attacker has: your release artifact. Each phase narrows raw signals into findings worth engineering time.

  1. 01

    Scope & authorize

    Provide APK/AAB and context. Define authorized targets, permitted test types, exclusions, source/API access, and test accounts where appropriate.

  2. 02

    Reconstruct the attacker view

    Inspect, extract, decompile, and fingerprint the release. Map Flutter, Android wrapper, configuration, services, native boundaries, and backend endpoints.

  3. 03

    Verify, don't just flag

    Manually inspect suspicious signals. Determine prerequisites, reachability, exploitability, impact, context, and whether a signal is only hardening advice.

  4. 04

    Report & fix

    Receive prioritized findings, evidence, attack path, reproduction information, impact, a concrete fix, and optional retesting.

FAQ

Before you send a release.

Need a different scope? Ask directly.

Is this an automated scan?

No. Automation may assist evidence collection, but the paid service is a manual security assessment performed by Mohamed. Findings are contextualized and verified rather than forwarded directly from a scanner.

What do you need from me?

At minimum, an APK or AAB you are authorized to have reviewed. Test credentials, source access, API documentation, and a staging environment can support a deeper assessment.

Can you review a competitor's Flutter app?

Publicly distributed artifacts and public information may be analyzed non-invasively. No intrusive testing against third-party infrastructure is performed without authorization.

Is this an OWASP-certified penetration test?

No invented badges or certifications. Where useful, findings can be mapped to recognized mobile-security categories and standards while the assessment remains focused on the real Flutter release.

Can you retest after fixes?

Yes. A retest can verify that fixes address the reported attack path without introducing new exposure.
