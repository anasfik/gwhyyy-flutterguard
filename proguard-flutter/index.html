ProGuard and R8 in Flutter: what they hide

Two toolchains get mixed up in Flutter release builds. R8 and ProGuard work on Java and Kotlin. Dart has its own obfuscator. Neither one encrypts what you ship.

By Anas Fikhi · 2 November 2026 · 7 minute read

The confusion is understandable. Flutter adds ProGuard rules, Gradle exposes minifyEnabled, and the Flutter build command has an --obfuscate flag. They sound like layers of the same defence. In practice they operate on different code, at different stages, with different limits.

Two toolchains, one APK

LayerToolWhat it changes
Java and KotlinR8 (ProGuard rules)Shrinks, optimises and renames Android classes, methods and fields.
Dart applicationflutter build --obfuscateRenames Dart symbols in the AOT snapshot so stack traces and identifiers are less readable.
Assets and stringsNothing by defaultFile names, JSON, images and string literals remain as built.

The Dart snapshot ends up in libapp.so. R8 does not rewrite it. A ProGuard rule cannot protect a Dart string, and Dart obfuscation does not rename your Kotlin plugin classes.

What R8 and ProGuard do

ProGuard was the original shrinker, optimiser and obfuscator for Android bytecode. R8 replaced it in the Android build pipeline and reads the same keep rules. When shrinking is enabled, R8 removes unused classes and members, rewrites what remains, and renames surviving symbols to short names. Resource shrinking can remove unused resources alongside it.

The lifecycle matters: R8 runs before the DEX is written, and it must preserve entry points that Android, reflection or a plugin look up by name. That is why projects carry keep rules. A missing rule can break a feature at runtime while the build still succeeds. Adding rules to fix that can also make more names readable again.

android {
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
        }
    }
}

Shrinking is worth doing for size and for removing dead code. Treat the obfuscation it provides as a speed bump for Java and Kotlin, not as a secret store.

What Dart obfuscation does

Flutter's --obfuscate flag renames Dart symbols in the compiled application. Pair it with --split-debug-info so you keep the symbol file needed to read crash reports:

flutter build apk --release \
  --obfuscate \
  --split-debug-info=build/symbols

The Flutter documentation is direct about the limits: obfuscation makes symbols harder to read and is not a security measure. String literals are not encrypted. Asset names are not changed. URLs, header names and key-like values can still be recovered from libapp.so with strings.

Obfuscation also raises the cost of your own debugging. Without the matching symbol file, a release stack trace is a list of short names. Keep the symbols with the release, not in the repository.

What still shows up in the APK

  • String literals. Endpoints, query parameters, header names and hardcoded values survive both toolchains.
  • Compile-time configuration. Values passed with --dart-define are built into the binary. They are not runtime secrets.
  • Asset files. JSON, fonts, images and bundled configuration are extractable. flutter_assets/ is a directory, not a vault.
  • Dependency clues. NOTICES.Z, package: URIs and readable symbols identify packages and SDKs.
  • Android surface. The manifest, exported components, permissions and network security configuration are unchanged by Dart obfuscation.
  • Signing material. The certificate still names the signer and the signature schemes still describe the build.

If a value cannot be public, it should not be in the client. Obfuscation changes how quickly someone reads the artifact, not whether they can.

How to check your own build

  1. Build the release twice, once without --obfuscate and once with it, and keep both artifacts.
  2. Run strings over libapp.so from each build and compare the readable symbols. String literals should still be there; identifier names should not.
  3. List flutter_assets/ and confirm nothing private is bundled.
  4. Read the manifest for debuggable flags, cleartext traffic and exported components.
  5. Open the APK with an on-device inspector and record what a reviewer would see.

Common mistakes

  • Assuming ProGuard hides Dart code. It does not touch libapp.so.
  • Putting an API key in --dart-define and calling it hidden. It is a compile-time constant in the binary.
  • Treating obfuscation as a substitute for server-side authorization. The client is not a trust boundary.
  • Enabling R8 without the keep rules a reflection-based plugin needs, then shipping a runtime failure.
  • Storing secrets in assets, JSON or a bundled .env file.
  • Auditing only the repository and never the signed artifact users install.

What to do instead

Keep secrets on the server. Issue short-lived, scoped tokens to the client and enforce authorization where the data lives. Use R8 and --obfuscate to raise the cost of reverse engineering and to reduce size, then verify the result with the same static checks an outsider would run. For the broader checklist, see what a release APK exposes.

Obfuscation is measurable. If a Dart symbol name is still readable in libapp.so, the build did not obfuscate. If a URL is still readable after obfuscation, that is expected: the flag was never meant to remove it.
